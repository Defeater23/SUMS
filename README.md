# SUMS — University Resource Management System

SUMS is a full-stack application for booking, approving and analysing university
resources: classrooms, laboratories, seminar rooms, meeting rooms, auditoriums
and portable equipment.

It is a working database-backed application, not a UI prototype. Every screen
reads and writes real PostgreSQL data through Supabase, every permission is
enforced in the database with Row Level Security and `SECURITY DEFINER`
functions, and double bookings are prevented by a database constraint rather
than by frontend checks.

---

## 1. Project overview

### What it does

| Area | Capability |
| --- | --- |
| Authentication | Email + password sign-up, sign-in, sign-out, persistent sessions, password reset, protected routes, profile management |
| Roles | `student`, `faculty`, `admin` — enforced server-side, never only by hiding buttons |
| Resources | Catalogue with search, filters (category, building, capacity, availability), detail pages, administrator CRUD, deactivation instead of deletion |
| Bookings | Date/time selection, live availability, server-side validation, status history, cancellation within policy |
| Overlap prevention | GiST exclusion constraint on a generated `tstzrange`; concurrent requests cannot double-book |
| Approvals | Administrator queue, approve/reject with a reason, transactional availability re-check at decision time |
| Notifications | Database-backed in-app notifications generated by triggers for booking events |
| Dashboard | Role-specific statistics computed from real records (no hardcoded numbers) |
| Analytics | Booking trends, status/category distribution, most-booked resources, utilisation, decision trends, feedback summary, with date-range filtering |
| Feedback | Rating + comment for resources the user actually booked; administrators review and annotate |
| Settings | Profile, appearance (light/dark), password, institution booking rules, resource categories |
| Audit | Append-only audit trail for privileged resource and account changes |

### Roles in brief

- **Student** — browse resources, request bookings, view and cancel their own
  bookings, receive notifications, submit feedback for resources they used.
- **Faculty** — everything a student can do, plus the ability to book
  approval-free resources without queueing behind routine requests, and to see
  departmental context on their own bookings.
- **Administrator** — manage the resource catalogue and categories, approve or
  reject requests, manage users and roles, review feedback, configure
  institution rules, and read analytics.

## 3. Architecture

```
Browser (React + TypeScript)
  │
  ├── AuthContext ──────── Supabase Auth (session, JWT, password reset)
  │
  ├── feature/api.ts ───── @supabase/supabase-js
  │                          │
  │                          ├── SELECT  → Row Level Security decides what is visible
  │                          └── RPC     → PL/pgSQL functions (all state changes)
  │
  └── Realtime ─────────── postgres_changes on `notifications`
```

### Key architectural decisions

1. **All state changes are server-side.** `bookings` and `feedback` have no
   `INSERT`/`UPDATE`/`DELETE` policies at all. A client cannot create a booking,
   approve it, or bypass the overlap constraint by writing to the table — it must
   call a validated function.
2. **The database is the authorization boundary.** The UI hides what a role
   cannot use, but the same rules are re-applied in RLS policies and inside every
   function, so a hand-crafted request fails.
3. **Overlap prevention is a constraint, not a query.** `bookings.occupied_period`
   is a stored generated `tstzrange`, non-null only for `approved`/`completed`
   rows, protected by a GiST exclusion constraint. Two concurrent transactions
   cannot both succeed; the loser receives SQLSTATE `23P01`.
4. **No mock data path.** If Supabase is not configured, the application renders
   a configuration screen instead of pretending to work.
5. **Feature folders.** Each feature owns its `api.ts` (data access), hooks and
   pages; shared presentation lives in `src/components/ui`.

## 4. Database schema

Eight tables, all with RLS enabled.

| Table | Purpose | Notes |
| --- | --- | --- |
| `profiles` | One row per auth user | `role` is the authorization source of truth; protected by a trigger |
| `resource_categories` | Category dictionary | `unique (name)` |
| `resources` | Bookable catalogue | Operating hours, durations, advance window, `equipment text[]`, `is_active` |
| `bookings` | Central transactional table | `occupied_period` generated column + GiST exclusion constraint |
| `notifications` | In-app notifications | Written by triggers, read by the user |
| `feedback` | Ratings and comments | `unique (user_id, booking_id)` — one review per booking |
| `audit_events` | Append-only audit trail | `bigserial`, admin-readable |
| `app_settings` | Single-row institution configuration | Time zone, opening hours, slot size, cancellation cutoff, auto-approval roles |

### Constraint highlights

```sql
-- bookings: only approved/completed rows hold a slot
occupied_period tstzrange generated always as (
  case when status in ('approved','completed')
       then tstzrange(starts_at, ends_at, '[)') end
) stored,

constraint bookings_time_order_chk check (ends_at > starts_at),
constraint bookings_no_overlap exclude using gist (
  resource_id with =,
  occupied_period with &&
)
```

- `resources.category_id` → `resource_categories(id) ON DELETE SET NULL`
- `bookings.resource_id` → `resources(id) ON DELETE RESTRICT` (history is never destroyed)
- `bookings.user_id` → `profiles(id) ON DELETE CASCADE`
- `notifications.booking_id` → `bookings(id) ON DELETE CASCADE`
- `profiles.id` → `auth.users(id) ON DELETE CASCADE`

### Indexes

Partial and composite indexes cover the real access patterns: pending bookings,
upcoming approved bookings, unread notifications, per-user booking history,
`resources` by category/active state, and a GIN index on `equipment`.

## 5. Migration and seed instructions

### Option A — Supabase CLI (recommended for local development)

```bash
supabase start                     # starts PostgreSQL 15 + Auth + Studio locally
supabase db reset                  # applies supabase/migrations/*.sql in order, then seed.sql
```

`supabase/config.toml` sets the local API port to 54321, Studio to 54323, and the
auth site URL to `http://localhost:5173`.

### Option B — an existing Supabase project

Run the files in `supabase/migrations/` **in filename order** using the SQL
editor (or `supabase db push`), then run `supabase/seed.sql`:

1. `20260101000000_extensions_and_types.sql` — `pgcrypto`, `btree_gist`, enums, `app_settings`, helper triggers
2. `20260101000100_tables.sql` — the eight tables, constraints, generated column, exclusion constraint
3. `20260101000200_indexes.sql` — indexes
4. `20260101000300_functions_and_logic.sql` — authorization helpers, triggers, booking/approval/notification logic, grants
5. `20260101000400_rls_policies.sql` — Row Level Security policies
6. `20260101000500_analytics.sql` — dashboard and analytics functions
7. `seed.sql` — institution settings, 6 categories, 14 resources (idempotent)

All migrations are written to be safe to re-run (`create or replace`,
`if not exists`, `on conflict`).

### Demo data

```bash
node scripts/seed-demo-data.mjs
```

Creates five demo accounts (`admin@sums.demo`, `faculty@sums.demo`,
`faculty2@sums.demo`, `student@sums.demo`, `student2@sums.demo`), a mix of
pending/approved/rejected/cancelled/completed bookings, and feedback entries.
The script is idempotent: rows carrying the `SUM-DEMO` marker are replaced on
each run, and nothing else is touched.

It requires `SUPABASE_SERVICE_ROLE_KEY` and `DEMO_PASSWORD` from the
environment. **No credentials are stored in this repository**, and the script
refuses to run if a service-role key is found in a `VITE_` variable.

## 6. Authentication and role setup

### Sign-up

Registration collects name, email, department and a role choice limited to
**student** or **faculty**. The choice is passed as `requested_role` metadata
and honoured by the `handle_new_user` trigger **only** for those two values.
Anything else falls back to `student`, so a crafted sign-up request cannot
create an administrator.

### Session handling

The client uses PKCE, persists the session under `sums.auth.token`, refreshes
tokens automatically and restores the session on reload. Protected routes render
inside `RequireAuth`; guest pages render inside `GuestOnly`.

### Becoming an administrator

Roles are changed **only** through:

- the User Management screen (`public.set_user_role(uuid, user_role)`), which
  requires the caller to be an administrator, or
- a service-role provisioning run (`scripts/seed-demo-data.mjs`, or the SQL
  editor) used to appoint the first administrator.

Both paths are guarded: a `BEFORE UPDATE` trigger rejects any role or
`is_active` change made by a non-administrator, and the RPCs refuse to remove
the last active administrator.

### Password reset

`/forgot-password` sends a Supabase reset e-mail; `/reset-password` exchanges the
recovery code for a short-lived session (the client is configured with
`detectSessionInUrl`), lets the user set a new password, then signs out and
redirects to sign-in. Expired links are detected and explained.

## 9. Server-function documentation

All functions live in the `public` schema. Helper functions are `SECURITY
DEFINER` with a pinned `search_path`; `EXECUTE` is revoked from `public` and
`anon` and granted explicitly to `authenticated`.

### Authorization helpers

| Function | Returns | Notes |
| --- | --- | --- |
| `current_user_role()` | `user_role` | Role of `auth.uid()` |
| `is_admin()` | `boolean` | Used by RLS policies and functions |
| `is_faculty_or_admin()` | `boolean` | Departmental actions |
| `is_service_request()` | `boolean` | True for service-role (server-side) requests; not executable by `authenticated` |
| `app_timezone()` | `text` | Institution time zone from `app_settings` |

### Booking lifecycle (RPC — call with `supabase.rpc(...)`)

| Function | Purpose |
| --- | --- |
| `validate_booking(p_resource_id, p_starts_at, p_ends_at, p_attendees)` | Ordering, active/available resource, operating hours, day allowed, lead time, advance window, minimum/maximum duration, capacity, overlap and approval requirement |
| `create_booking(p_resource_id, p_starts_at, p_ends_at, p_purpose, p_attendees)` | Re-validates, inserts as `pending` or `approved`, translates SQLSTATE `23P01` into a friendly message, notifies the requester and administrators |
| `cancel_booking(p_booking_id, p_reason)` | Owner or administrator, respects `cancellation_cutoff_mins`, frees the slot, notifies |
| `decide_booking(p_booking_id, p_decision, p_reason)` | Administrator only; **re-checks availability inside the same transaction**, so an approval can never create an overlap |
| `complete_past_bookings()` | Moves finished approved bookings to `completed`; also drops the slot from the exclusion constraint's point of view |
| `get_resource_availability(p_resource_id, p_from, p_to)` | Busy periods for a resource. Returns start/end only — no personal data about other users |

### Notifications and feedback

| Function | Purpose |
| --- | --- |
| `mark_notifications_read(p_ids uuid[] default null)` | Marks the supplied ids, or all of the caller's notifications when `null` |
| `submit_feedback(p_resource_id, p_rating, p_comment, p_booking_id default null)` | Requires the caller to have booked that resource; one review per booking |
| `review_feedback(p_feedback_id, p_notes)` | Administrator review with notes |

### Administration

| Function | Purpose |
| --- | --- |
| `set_user_role(p_user_id, p_role)` | Administrator only; refuses to demote the last active administrator; writes an audit event |
| `set_user_active(p_user_id, p_is_active)` | Administrator only; same last-administrator guard |

### Analytics (read-only, all authorized server-side)

| Function | Output |
| --- | --- |
| `fn_my_dashboard_stats()` | Upcoming, pending and approved counts for the caller, plus unread notifications |
| `fn_admin_dashboard_stats()` | Active resources, total bookings, pending approvals, upcoming bookings, total users |
| `fn_analytics_booking_trends(p_from, p_to)` | Bookings created and completed per period |
| `fn_analytics_status_distribution(p_from, p_to)` | Counts per status |
| `fn_analytics_category_distribution(p_from, p_to)` | Bookings per resource category |
| `fn_analytics_top_resources(p_from, p_to, p_limit)` | Most-booked resources |
| `fn_analytics_resource_utilization(p_from, p_to)` | Booked hours vs. available hours per resource, calculated in the institution time zone and excluding non-operating weekend days |
| `fn_analytics_decision_trends(p_from, p_to)` | Approvals and rejections per period |
| `fn_feedback_summary()` | Feedback volume, average rating, open count |

### Edge Function

`supabase/functions/notify-booking` exists as an **optional** e-mail hook. It is
disabled unless `BOOKING_NOTIFY_WEBHOOK_SECRET` is configured, it refuses
requests without that secret, and it reports `email_provider_not_configured`
rather than pretending to have sent anything. In-app notifications do not depend
on it.

## 10. Booking policy (pending vs. reserved)

- A **pending** request does **not** hold a slot. Pending rows have a `NULL`
  `occupied_period`, so they are outside the exclusion constraint.
- Only **approved** and **completed** bookings reserve time.
- Availability is therefore re-checked **inside the approval transaction**
  (`decide_booking`). If the slot was taken while a request waited, the approval
  fails with a clear message and the status stays `pending`.
- Cancelling an approved booking clears the slot immediately because the
  generated column becomes `NULL` for non-holding statuses.
- The UI mirrors these rules for guidance: `get_resource_availability` lists
  busy slots, and the booking dialog refreshes them after a successful request.
  The database remains authoritative.

## 12. Security review

| Check | Status |
| --- | --- |
| Row Level Security enabled on every table | Yes — all eight tables |
| Every table has at least one policy | Yes |
| `bookings` / `feedback` cannot be written directly by clients | Yes — no INSERT/UPDATE/DELETE policies; writes go through validated functions |
| Administrator privileges are not self-assignable | Yes — sign-up metadata limited to student/faculty; `BEFORE UPDATE` trigger blocks non-admin role changes |
| Role changes require an administrator | Yes — `set_user_role` plus the trigger |
| The last active administrator cannot be removed or demoted | Yes — guarded in `set_user_role` / `set_user_active` |
| Service-role key never reaches the frontend | Yes — read from `process.env` by the seeding script only; the app uses `VITE_` anon credentials only, and the script fails if the key appears in a `VITE_` variable |
| Inputs validated | Yes — Zod on the client, re-validated in PL/pgSQL |
| Backend verifies authorization | Yes — every function checks `auth.uid()` and role; RLS covers direct reads |
| Sensitive data not unnecessarily exposed | Availability returns busy periods only, not other users' details; `audit_events` is administrator-only |
| Booking conflicts prevented in the database | Yes — GiST exclusion constraint, not a frontend check |
| Error messages do not leak internals | Yes — SQLSTATE mapping plus a filter that replaces raw SQL errors |
| Function privileges minimized | Yes — `EXECUTE` revoked from `public`/`anon`, granted explicitly to `authenticated` |
| Anonymous access | Revoked on all tables and functions |

### Privilege-escalation guard

```sql
if new.role is distinct from old.role and not public.is_admin() then
  raise exception 'Only administrators may change user roles.' using errcode = '42501';
end if;
```

`is_service_request()` allows trusted server-side tooling to appoint the first
administrator. That is the only path that bypasses the guard, and it requires the
service-role key, which is never shipped to a browser.

## 13. Known limitations

Recorded honestly rather than glossed over.

1. **No live Supabase project was connected in this environment.** The
   migrations, functions, policies and analytics SQL are complete and were
   reviewed, but they have not been executed against a hosted project from here,
   and the application has **not** been deployed. Sections 5 and 8 describe
   exactly what to run.
2. **End-to-end tests were not executed.** Playwright specs are committed, but
   without a configured project and demo credentials they skip. The unit and
   component suites were run (see the verification log).
3. **No version-control integration.** The environment has no `git` binary, so
   no commits, branches or GitHub integration are included. The project is
   plain files on disk.
4. **E-mail and push notifications are not enabled.** In-app notifications are
   real and trigger-driven. The `notify-booking` Edge Function is a stub that
   reports `not_configured` unless an operator supplies provider credentials and
   a template — nothing in the UI claims e-mail delivery works.
5. **Resource images are URL-based only.** There is no file upload; an
   administrator can point a resource at an external image URL.
6. **`complete_past_bookings()` must be scheduled.** It is exposed but nothing
   calls it on a timer, so bookings stay `approved` until it runs. Add a
   `pg_cron` schedule (`select cron.schedule('sums-complete', '*/15 * * * *',
   'select public.complete_past_bookings()')`) in production. Analytics and the
   dashboard treat `approved` past bookings sensibly in the meantime.
7. **Analytics aggregate in SQL and are not cached.** Fine at university scale;
   very large datasets would benefit from materialised views.
8. **Realtime covers notifications only.** Booking lists refresh on load and
   after actions rather than streaming changes.

### Toolchain corrections made to get here

- `@types/node` was added and `"node"` inserted into `compilerOptions.types`,
  which is what `vite.config.ts`, `playwright.config.ts` and the e2e specs
  require (`node:url`, `process.env`).
- `vite.config.ts` now imports `defineConfig` from `vitest/config` so the `test`
  block is typed.
- Vitest was moved from 2.x to 3.2.7. Vitest 2 pinned its own nested Vite 5,
  which made `vitest/config`'s plugin types incompatible with the project's
  Vite 6 and produced a spurious `TS2769` in `vite.config.ts`.
- The Supabase client is deliberately untyped, so `data` is `any`; the newer
  PostgREST typings reject `.returns<T>()` in that situation with a
  `CheckMatchingArrayTypes` error. Each `api.ts` module now narrows the payload
  once, at the boundary (`(data ?? []) as T[]`, `data as T`), which typechecks
  and keeps a single documented place where server rows become typed models.

### Environment note (does not affect the application)

On this machine, spawning `cmd.exe` from a Node child process fails with
`EPERM` (the sandbox denies shell spawns). Vite performs one *optional* Windows
probe, `exec('net use')`, used only to detect mapped network drives; when that
spawn throws, the error propagates and aborts the run. The verification runs
above were therefore launched with `ComSpec` pointed at `node.exe` so the probe
fails harmlessly instead of throwing. Nothing in `src/`, `supabase/`, the tests
or the build config depends on this; it is a property of this sandbox alone.
